## legacy-portal: `rearchitect`

Owner team: Customer Portal. The questionnaire says `rehost`: "Lift the VM to EC2 as it is". Agrees: **no**.

**Rationale.** Rearchitect requires clean seams and a parity corpus that can prove each port. Both exist. Seams: each of the three bounded contexts has its own package, its own /api/* route prefix and its own schema, with no cross-context foreign keys (README.md:16-20; initdb.sql:3-5; @Table schemas at Announcement.java:15, UserPreference.java:12, Feedback.java:15; AnnouncementController.java:20; FeedbackController.java:21). Parity corpus: requests.json holds 95 ordered cases (common 10, announcements 36, preferences 20, feedback 29) with recorded Java responses. Both files are checksum-locked in SHA256SUMS:1-2, and replay.py refuses to run on a checksum mismatch (replay.py:213-217). It compares status, media type and body (replay.py:117-125). That corpus has already proven a per-context Lambda port at 95/95 identical (services/legacy-portal-lambda/REPORT.md:11-18), against Aurora PostgreSQL 16.13 Serverless v2 built from Hibernate's own DDL (aurora.tf:37-45; variables.tf:41-52, 60-64; schema.sql:10-12). Retire is ruled out: the 90 days of logs hold 162,000 requests, 107,915 of them from browser user agents and none from cron, curl or bot agents. Rehost is not supported: the rubric needs a reason the code cannot change cheaply, and the evidence says the opposite. The app is a small Spring Boot jar with unit tests, a CI build (ci.yml:369-381), and an existing port. Replatform is weaker than rearchitect, though a managed Postgres target exists: it would keep the end-of-life Java 11 / Spring Boot 2.7.18 monolith (pom.xml:10-11, 25-28), which then still needs its upgrade path. Disposition none does not apply. The app stores user feedback and preferences (Feedback.java:22-29; schema.sql:11-12), but nothing in the app, its schema, its scripts or its Terraform names an approval gate on deleting that data (grep for approv/legal hold/retention/purge found only log-group retention settings). The app is not routed through the API gateway: ServiceRoutes has no legacy-portal or /portal prefix (config.go:113-130), and no Helm chart or root compose file references it.

**Caveat.** Before cutover: (1) Reconcile the access logs with the code. All 162,000 logged rows hit /portal/{accounts,orders,catalog,login}. None of those routes exist in the controllers, which serve only /api/announcements, /api/preferences, /api/feedback and /health. The only place those paths appear in the repo is the log generator. So either the real /portal/* front end lives somewhere not in this repo, or the logs don't describe this code. Confirm which before moving any live traffic. (2) Find out who the okhttp/4.12.0 client is (54,085 rows, a programmatic caller) and give it a cutover plan. Nothing in the repo or the gateway names it. (3) Migrate the stateful data (the feedback.feedback and user_preferences.user_preference rows holding user_id and free-text messages) to the Aurora PostgreSQL 16 target, with row-count reconciliation. (4) The port must not carry forward the end-of-life and vulnerable stack. Java 11 moves to 21 (the Lambda poms already use release 21). Spring Boot 2.7.18 (OSS support ended) moves to 3.2+, with javax.* changed to jakarta.*. Transitive commons-text 1.9 (CVE-2022-42889, via commons-configuration2 2.8.0) moves to 1.10.0 or later. The unauthenticated /health must stop returning the interpolated operator banner. (5) Reset the target's schemas before each replay, and keep requests.json and java-reference.json unchanged under their SHA256SUMS. (6) Investigate the 5.05% HTTP 500 rate before parity sign-off.

**Where the questionnaire is wrong.** The questionnaire says rehost: 'Lift the VM to EC2 as it is'. That fails the rubric's rehost condition, because there is no reason the code cannot change cheaply. It is a small Spring Boot 2.7 jar with three cleanly separated contexts (README.md:16-20), a CI build (ci.yml:369-381), and a checksum-locked 95-case parity corpus. The corpus has already proven a per-context Lambda + Aurora port at 95/95 identical (services/legacy-portal-lambda/REPORT.md:11-18). Lifting it 'as it is' would also carry over known liabilities. It runs on Java 11 and Spring Boot 2.7.18, both of which the repo itself marks as legacy upgrade targets (pom.xml:10-11, 25-28; Dockerfile:5,16; README.md:72-76). It pulls in commons-text 1.9 transitively via commons-configuration2 2.8.0, which is inside the CVE-2022-42889 vulnerable range (pom.xml:31, 53-57; advisory.yaml:6-7, 15-17; security/deps/expected/legacy-portal.json:7). The unauthenticated /health endpoint returns the interpolated operator banner (HealthController.java:21-27; portal-settings.properties:1-6). The default datasource is in-memory H2, so data does not survive a restart (application.yml:11). The repo's EC2 'as it is' unit installs a self-managed postgresql15-server and Corretto 11 on the host (infrastructure/terraform/legacy-portal-ec2/files/user_data.sh:9), and the repo's own docs describe that EC2 stack only as a 'before state' that a later session moves to Lambda (docs/aws-legacy-portal/README.md:154). That makes it a stepping stone, not a target.

## report-service: `replatform`

Owner team: Reporting. The questionnaire says `retire`: "Nobody calls it". Agrees: **no**.

**Rationale.** Retire fails the rubric's first condition. There is user traffic: 12,600 requests over 90 days (140 a day) to /api/v1/reports and /api/v1/reports/scheduled. 8,340 come from browser user agents and 4,260 from okhttp. Every one returned 404 at the api-gateway, because ServiceRoutes has no /api/v1/reports prefix (config.go:113-129), even though REPORT_SERVICE_URL is still configured (config.go:80) and the service mounts that prefix (ReportController.java:53). The route was removed in ab390f72f. Unserved demand is still demand, so the cause is a routing regression, not an unused application. The admin dashboard still calls the API too (migration-api.service.ts:22,76-82). Replatform's conditions are met. Each stateful dependency has a managed target: the PostgreSQL otterworks_reports database (application.properties:12) goes to the RDS postgres module (modules/database/main.tf:55), and the archive read path, which only SELECTs (100_grants.sql:12-13; application.properties:42-43), goes to ARCHIVE_STORE=postgresql. Each end-of-life component has a named upgrade path: Java 1.8, Spring Boot 2.5.15 and Commons Lang 2.6 (pom.xml:10-12,25-27,36-39) are covered by UPGRADE_GUIDE.md axes 1-7 (:13-14,27,68,401). Rearchitect is not needed, and none does not apply. The service's own reports table has no deletion gate that needs a person's approval, and the archive data belongs to db2-retention-archive. Parity risk for the replatform: the guide's java.time snippet (UPGRADE_GUIDE.md:450-451) uses ZoneId.systemDefault(). Today the code formats in UTC (ReportDateUtils.java:30,35), and TZ is America/Chicago in Helm and Compose (values.yaml:66; docker-compose.yml:403).

**Caveat.** First restore the /api/v1/reports gateway route; it was removed from ServiceRoutes, which is why 100% of 12,600 user requests got a 404. Managed targets for the stateful dependencies: the otterworks_reports PostgreSQL database goes to the RDS PostgreSQL module, and the archive read path goes to ARCHIVE_STORE=postgresql on RDS. Named upgrade path for the end-of-life stack: follow UPGRADE_GUIDE.md axes 1-7 (Java 1.8 to 17, Spring Boot 2.5.15 to 3.2+, javax to jakarta, Commons Lang 2.6 to 3). Fix the guide's java.time step before porting: it formats DISPLAY_FORMAT in ZoneId.systemDefault(), but the current code pins UTC, and the deployment sets TZ=America/Chicago. As written, the display column would shift by 5-6 hours after the upgrade. Use ZoneOffset.UTC and prove it with a parity replay.

**Where the questionnaire is wrong.** The questionnaire says retire because 'Nobody calls it'. The logs show 12,600 calls in 90 days from browsers and an okhttp client, all failing with 404 at the gateway (log query).
