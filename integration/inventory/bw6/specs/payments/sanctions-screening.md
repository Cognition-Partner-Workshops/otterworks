## 4. Transaction boundaries

- No `bpws:scope` and no transaction declaration: the activities sit directly in the `Execute` sequence [`integration/legacy-bw6/Processes/payments/sanctions-screening.bwp:L11`](../../../../legacy-bw6/Processes/payments/sanctions-screening.bwp#L11).
- Order: Receive → MapRecord → DispatchRequest (HTTP, non-transactional) → Insertscreeningresults (`AUTO_COMMIT`, committed on execution) → Publish [`integration/legacy-bw6/Processes/payments/sanctions-screening.bwp:L13-L34`](../../../../legacy-bw6/Processes/payments/sanctions-screening.bwp#L13-L34).
- **Not covered:** the DB insert commits before the publish. **Inference:** a failure in Publish leaves the `screening_results` row committed with no outbound message. Redelivery then re-runs the insert, which violates the `(flow, request_id)` primary key [`integration/legacy-bw6/Database/schema.sql:L31-L39`](../../../../legacy-bw6/Database/schema.sql#L31-L39), so the message ends in `HB.UNDLV`.
