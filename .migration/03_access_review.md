## 2. The specific checks

1. **Does the SUBSCRIPTIONS status write in the packages carry `cascades` → `trg_subscriptions_hist`, so the proposer sees `written_together` / `via_trigger` for SUBSCRIPTIONS_HIST?** — **Yes.** `pkg_plans.sp_change_plan` UPDATE (`packages/02_pkg_plans.sql:91-94`, `ap-a7af1a6156`) and `pkg_dunning.sp_suspend_overdue` UPDATE (`packages/05_pkg_dunning.sql:82-84`, `ap-d3754b6b8a`) both carry `cascades: ["ap-bdfdef0db0"]`, and so does the app's direct UPDATE (`app/backends/oracle.py:68-73`, `ap-f95317f034`). `ap-bdfdef0db0` is `trg_subscriptions_hist` AFTER UPDATE OR DELETE ON subscriptions (`schema/01_tables.sql:206-207`) inserting the `:OLD` row into SUBSCRIPTIONS_HIST (`:213-222`); it is not autonomous, so the child write is in the caller's transaction. All three are confirmed and pinned. Caveat: the INSERTs into SUBSCRIPTIONS also carry the same cascade (`ap-875f85e898`, `ap-4de28fdf15`, `ap-453b668254`, `ap-0f6d62e335`, `ap-1bee089176`) and that is wrong — the trigger has no INSERT event — so those five are unconfirmed (§3.2).
2. **Same for CUSTOMER_MASTER → `trg_customer_master_hist` → CUSTOMER_MASTER_HIST?** — **No valid cascade exists.** `trg_customer_master_hist` is AFTER UPDATE OR DELETE ON customer_master (`schema/02_horror.sql:358-359`, INSERT customer_master_hist `:365-372`, `ap-dbf1b410e9`). The only CUSTOMER_MASTER writes in any root are the fixture INSERTs (`schema/03_seed_static.sql:77-98` `ap-c103a40ece`; `schema/04_upgrade_static.sql:101-127` `ap-06d2eaab32`), both `deploy_script: true`, and the scanner attached the cascade to them even though an INSERT does not fire this trigger — so those two are unconfirmed. No package, trigger, job or app statement updates or deletes CUSTOMER_MASTER (grep over `packages/`, `schema/`, `app/`, `etl/`; register O-6). The proposer therefore has **no** `written_together`/`via_trigger` evidence for CUSTOMER_MASTER_HIST, and the recon will grade that cascade UNVERIFIED; the trigger row itself is confirmed `cold` so the relationship stays on record.
3. **Who writes BILLING_AUDIT_LOG, in-transaction or detached?** — Exactly one writer: `pkg_ow_util.log_msg` (`packages/01_pkg_util.sql:70-71`, `ap-779ce5b5b7`), declared `PRAGMA AUTONOMOUS_TRANSACTION` (`:67`) with its own `COMMIT` (`:72`) and `WHEN OTHERS THEN ROLLBACK` (`:76`) → **detached** from every caller's transaction; a caller rollback never removes the audit row and a failed log never fails the caller. Callers: `pkg_plans.fn_list_plans` `:23`, `sp_change_plan` `:84`; `pkg_rating.compute_rating` `:117`, `sp_finalize_rating` `:216`; `pkg_invoicing.sp_issue_invoice` `:192`; `pkg_dunning.sp_schedule_dunning` `:66`, `sp_suspend_overdue` `:96`. `log_id` is assigned by `trg_billing_audit_log_id` BEFORE INSERT (`schema/01_tables.sql:179-186`, no candidate — assigns `:NEW` only). The only other DML is the retention DELETE in `JOB_PURGE_AUDIT_LOG` (`schema/04_jobs.sql:24`, `ap-e7b18e81b8`, own COMMIT inside the job block). The scanner emits no `txn`/detached marker for routine-level autonomous transactions (§3.3), so `05_decisions.md` must carry the detached reading explicitly.
4. **Are the INVOICE_HEADER → INVOICE_LINE reads filtered on every parent-key column (per-parent evidence)?** — **No.** The one read touching both (`app/reports.py:55-81`, `ap-89c88ad4c6`) filters on `h.batch_no = :batch_no` (`:70`) and joins `h.invoice_id = l.invoice_id` (`:71`); there is no equality on `INVOICE_LINE.INVOICE_ID` to a parameter, and no `join_edges` because the census has no INVOICE_HEADER→INVOICE_LINE relationship (`invoice_line.invoice_id` is an unenforced pointer, `schema/02_horror.sql:406`). It is a batch-scoped read-together over the denormalised estate, not per-parent evidence. The ETL extract (`etl/legacy-extra/tools/oracle_custbill_extract.py:15-28`, `ap-fa4086177d`) reads INVOICE_HEADER with CUSTOMER_MASTER/TENANTS and never touches INVOICE_LINE. By contrast the transactional pair **is** per-parent: `pkg_invoicing.fn_invoice_lines` reads INVOICE_LINES `WHERE invoice_id = :inv` (`packages/04_pkg_invoicing.sql:106-109`, `ap-620d0a2057`, FK `FK_IL_INVOICE`), and `sp_issue_invoice` deletes/inserts INVOICE_LINES by `invoice_id` in the same transaction as its INVOICES write (`:150`, `:157-163`, `ap-5c6c87e418`, `ap-56d46b7c81`).
5. **Is ENTITY_ATTR_VALUE read with the parent entity or alone?** — **With the parent, via a second statement keyed by the parent id.** `GET /customer` (`app/facade.py:277-301`) first reads CUSTOMER_MASTER by tenant (`:287`, `ap-e45fe9768e`) and then reads ENTITY_ATTR_VALUE `WHERE entity_type = 'CUSTOMER' AND entity_id = :1 ORDER BY eav_id` with `:1 = cust_id` (`:294-297`, `ap-6c1786cb2d`). ## 3. Scanner misses and misattributions (input to `05_decisions.md` §5)

Statements and facts in the packages, triggers, jobs and callers that produced no candidate or a wrong one. Nothing below was patched in the JSON.

1. **Triggers with no candidate.** `trg_billing_audit_log_id` (`01_tables.sql:179-186`, BEFORE INSERT, assigns `seq_billing_audit_log.NEXTVAL`), `trg_sub_no_uncancel` (`:228-236`, BEFORE UPDATE OF status_cd ON subscriptions, raises when a cancelled row is reactivated), `trg_customer_master_seq` (`02_horror.sql:346-356`), `trg_entity_attr_value_seq` (`:391-399`). They contain no table DML, so the scanner has nowhere to hang them. Consequence: every SUBSCRIPTIONS status UPDATE (`ap-a7af1a6156`, `ap-d3754b6b8a`, `ap-f95317f034`) also fires `trg_sub_no_uncancel` and may fail — a business rule the proposal must re-implement (status transition guard), invisible in `cascades`; identity assignment for three tables is also invisible (`identity_capture` is only set where a sequence appears in DML).
2. **INSERT → AFTER UPDATE OR DELETE cascade over-approximation.** Seven INSERTs carry `cascades` to `trg_subscriptions_hist` or `trg_customer_master_hist` (ids in §0). The trigger objects correctly list `events: [update, delete]`; the cascade attachment ignores the event. Correct reading: these INSERTs fire no history trigger. The proposer must not read `written_together(SUBSCRIPTIONS→SUBSCRIPTIONS_HIST)` from an INSERT, and has no cascade at all for CUSTOMER_MASTER (check 2).
3. **No transaction context (`txn`) for Oracle.** The scanner never emits `txn` for PL/SQL or Python. Facts the proposer needs: (a) `pkg_ow_util.log_msg` is autonomous (check 3) — BILLING_AUDIT_LOG is **detached** from every caller; (b) `sp_issue_invoice` is one transaction spanning `sp_finalize_rating` (`04_pkg_invoicing.sql:134` → RATING_PERIODS/RATING_RESULTS writes), INVOICES insert/update, INVOICE_LINES delete/insert, CREDIT_NOTES update (`:136-190`), committed by the Python caller — `written_together` evidence for INVOICES+INVOICE_LINES, INVOICES+RATING_PERIODS/RATING_RESULTS and INVOICES+CREDIT_NOTES exists in source but not in the JSON; (c) `change_plan` runs the direct UPDATE and `pkg_plans.sp_change_plan` in one transaction (`oracle.py:68-80`, commit `:80`); (d) `ensure_tenant` inserts TENANTS and SUBSCRIPTIONS in one transaction (`oracle.py:141-169`, commit `:169`) — co-written evidence lost because `ap-4de28fdf15` is unconfirmed; (e) `JOB_PURGE_AUDIT_LOG` commits inside its block (`04_jobs.sql:24`); (f) usage ingest commits per event (`facade.py:412`).
4. **Python callers not harvested into `invoked_by`.** The caller pass reads only SQL/shell. `backends/oracle.py` calls every package routine (`callfunc`/`callproc` `:42, :48`; `fn_list_plans :57`, `fn_entitlement :61`, `sp_change_plan :77`, `fn_usage_rating :85`, `fn_usage_summary :92`, `sp_finalize_rating :99`, `fn_invoice_preview :106`, `sp_issue_invoice :113`, `fn_invoice_lines :119`, `fn_overdue_accounts :123`, `sp_schedule_dunning :127`, `sp_suspend_overdue :131`) from the Flask routes in `app.py:23-95`. So the dunning procedures look scheduler-only in the JSON when they are also HTTP-triggered, and every other package row has no `invoked_by` at all. `fn_usage_summary` (`ap-2b3995792f`) has no Flask route (`oracle.py:92` is only reachable from tests/CLI).
5. **No `join_edges`/`outer_edges` for non-FK joins.** CODES joins (all of them), INVOICE_HEADER⋈INVOICE_LINE (`reports.py:71`), INVOICE_HEADER⋈CUSTOMER_MASTER and INVOICE_HEADER⟕TENANTS (`oracle_custbill_extract.py:23-24`), CUSTOMER_MASTER→ENTITY_ATTR_VALUE (two statements) have no census relationship and therefore no edge. The proposer sees them only through `tables` co-occurrence.
6. **Filter vocabulary limits (accepted, not treated as wrong).** `IS NULL` is recorded as `eq` (every `ends_on IS NULL` / `sent_at IS NULL`); `OR` is flattened into independent `eq` entries (`ap-fa4086177d`: `h.batch_no = :b OR h.tenant_id = :a`); `NVL(ends_on, …) >= :on` becomes `ENDS_ON(NVL) range`. Index proposals must not treat `SUBSCRIPTIONS.ENDS_ON eq` as an equality key — it is a null-check.
7. **Statement truncation.** `statement` is cut at ~300 chars; `ap-fa4086177d` loses its `OR` branch and `ORDER BY`, the seed/upgrade `INSERT ALL`s lose their row lists. `sort` is still populated from the full parse except where an alias is used (`ORDER BY period_end` → dropped).
8. **Row limits not recorded.** `ROWNUM = 1` / `ROWNUM <= 1` (`02_pkg_plans.sql:47, :68`; `03_pkg_rating.sql:63, :178`; `04_pkg_invoicing.sql:43`; `oracle.py:153`), `ROWNUM <= 50/200` (`facade.py:222, :347`), `FETCH FIRST 1 ROWS ONLY` (`facade.py:126, :287`). Relevant to fan-out and index design.
9. **`INSERT … SELECT … FROM dual WHERE NOT EXISTS` writes inherit the subquery's filter** (`ap-7692fe1e9a`, `ap-d3eff9b330`, `ap-1bee089176`, `ap-5fa2aaf612`, `ap-221108f1cd`, `ap-dc751cd646`, `ap-06d2eaab32`, `ap-a82c763f48`). The filter is the dedupe key, not a row filter on the write. Accepted as a convention for the confirmed ones.
10. **Wrapper duplicates.** The `SELECT … FROM dual` select-list of those statements is emitted as a separate read whose `tables`/`filter` are copied from the nested subquery (8 ids in §0). Each duplicates a confirmed nested read; left unconfirmed so they are not double-counted.
11. **Scheduler precision.** `schedule_hint: daily` drops `BYHOUR=2;BYMINUTE=0` (`04_jobs.sql:15`) and `BYHOUR=3;BYMINUTE=30` (`:26`), and `enabled => FALSE` (`:16, :27`) is not recorded — the fixture never runs these jobs (register O-8).
12. **Locking and cursor semantics.** `FOR UPDATE` on `c_open_subs` (`02_pkg_plans.sql:80`) is not recorded; `WHERE CURRENT OF` is (`current_of`). The plan-change UPDATE therefore depends on a row lock the proposal must replace (single-document update or transaction).
13. **Intra-package call graph absent.** `compute_rating` ← `fn_usage_rating` (`03_pkg_rating.sql:126`), `sp_finalize_rating` (`:195`), `pkg_invoicing.compute_preview` (`04_pkg_invoicing.sql:48`); `sp_issue_invoice` → `sp_finalize_rating` (`:134`), `fn_invoice_preview` (`:152`) → `compute_preview` (`:77`). Rows are attributed to the routine that contains the SQL, so rating reads appear "rating-only" although every invoice issue executes them.
14. **Dead code.** `pkg_ow_util.f_code_desc` (`ap-d9d4207c37`) has no caller in any root; `f_str2dt`/`f_dt2str` in the same package have none either and no SQL. Its `hot` grade is the ticket rule, not evidence.
15. **Unbounded tenant scan.** `compute_rating`'s cursor reads all USAGE_EVENTS for the tenant (`03_pkg_rating.sql:77-78`) and filters by date in PL/SQL (`:79-80`) — the recorded filter (`TENANT_ID eq` only) is correct, but the proposal should index `(tenant_id, occurred_at)` rather than read the whole history.
16. **Roots not scanned.** `ops/*.txt` (see §0 deploy decisions), `startup/00_init.sh` (two `MERGE INTO fixture_meta`), `setup/01_users.sql` (no DML), Perl in `etl/legacy-extra` (no SQL — `03_access_scan_notes.md` §10.2). `testdata/legacy/oracle_billing_seed.py` builds INSERTs for the horror estate programmatically and was not a scan root; its CUSTOMER_MASTER/INVOICE_HEADER/INVOICE_LINE/ENTITY_ATTR_VALUE loads are the only bulk writers of those tables and are fixture-only.
