Unattended red-team run of the `mongo-migration` Devin plugin against the OtterWorks legacy Oracle billing estate (`services/legacy-billing/db/oracle/**`, schema `OW_BILLING`, mini fixture scale, read-only). Plugin under test: `Cognition-Partner-Workshops/mongo-migration-plugin` at branch `devin/1791335937-app-aware-modeling-next` with `865b105d695090615d1efa908fd9621e7bbd7bff` (PR #54, recon `index_keys` fix) cherry-picked on top, HEAD `6e96827f380046e3f0663f39a02cec930a99143d`; the recon harness from that clone is installed in `/home/ubuntu/.venvs/recon`. Target: shared Atlas M0 reached via the secret named `MONGODB_ATLAS_URI`; this run writes only to database `mmp_rt_b3_oracle`, keeps it under 10 MB, and never touches `ow_tp_*`, `ow_billing_*` or other `mmp_rt_*` databases. Run branch: `tp-run/mongodb-20261007T062215Z`; every PR targets it. Machine files written by the plugin land next to this file; findings about the plugin itself (wrong, blind, or manually corrected tool behaviour) are the main output of the run and are recorded in `05_decisions.md`.

## Recon tolerances (`recon_tolerances.json`, version 1, decision `d-tolerances: strict`)

`full_diff_row_threshold` 100000 (every fixture-scale collection gets a full keyed Tier 3 diff; Tier 1 row counts are always exact — the harness has no row-count slack), `numeric_abs_tol` 0 and `aggregate_rel_tol` 0 (field-level parity), `sample_size` 1000 (harness default, unused below the threshold), `source_concurrency` 1. Strings are compared only after the Oracle profile's canonicalization (`rstrip_spaces` for CHAR, `null_missing_equiv`): pass `--canonicalization skills/mongo-migration/profiles/oracle.md` unchanged in every recon run and name the rules per field in the mapping spec. Changing any value is a new version through a re-picked plan decision, never mid-run (see F5).

## Units and wave spec (s4.0-derive-units)

`units.json` is one unit per `map-draft-2` collection (16; `fixtureMeta` excluded, F45) with its source tables, the dependency edges and depth, and the document count / byte estimate from `fixture_counts.json` × `data_profile.json` `row_bytes` (embedded children minus orphans, extended-reference parent row as upper bound; max document ≤ 1,765 B on `invoiceHeader`, whole estate ≈ 0.61 MiB against the 10 MB budget). Depth: 0 = `codes`, `tenants`, `plans`, `customerMaster`, `billingAuditLog`; 1 = `ratingPeriods`, `creditNotes`, `usageEvents`, `notifications`, `subscriptions`, `invoiceHeader`, `customerMasterHist`; 2 = `invoices`, `subscriptionsHist`, `ratingResults`; 3 = `dunningAttempts`. Edges come from `decision.references` plus the two kinds the spec cannot record (`*Hist → base`, F52; `invoiceHeader → customerMaster` by CUST_ID, F48). The three loader-side obligations the spec cannot express (F47 `invoice_lines_orphaned`, 37 rows, embedded 1,463 + orphaned 37 = 1,500 `INVOICE_LINE`; F48 `customerMaster.tenantResolved`; F49 `signupDtRaw` + parsed `signupDt`, 41 unparseable) are on the owning unit under `loader_obligations`.

`waves/wave-1.json` is the single wave (`d-waves: one-wave`; the reference layer needs nothing landed first — every reference is the raw source key and both extended references are copied from the source parent row at load time, so depth orders batches and does not gate waves): 5 batches, 1–5 units each at one depth, `source_access: live`, `target_access: migration_cluster`, `auto_merge: false`, every batch pinned to `fixtures/mmp-rt-mini.json`, `map-draft-2` (`232efbd7…`) and tolerances `1` (`1a8ebb6c…`). `w1-b01` codes, tenants, plans, customerMaster, billingAuditLog · `w1-b02` ratingPeriods, creditNotes, usageEvents, notifications, subscriptions · `w1-b03` invoiceHeader, customerMasterHist · `w1-b04` invoices, subscriptionsHist, ratingResults · `w1-b05` dunningAttempts. Validate from `$HOME`: `python3 <plugin>/skills/wave-preflight/preflight.py --wave ~/repos/otterworks/.migration/waves/wave-1.json --root ~/repos/otterworks [--emit-tickets]` → `wave 1 OK: 5 batches, manifest_sha 790ff9c4775a` (the layout warning about `units.json`/`waves` is F59). `mmp_rt_b3_oracle.invoice_lines_orphaned` is deliberately **not** a wave `write_targets` entry: preflight validates it but `--grade` would fail the batch with `recon_results did not grade collections ['invoice_lines_orphaned']` (F57); it is the batch's `loader_obligations` entry instead, which the emitted ticket block omits.

## Wave 1 load (s4.1 — `w1-b01`: codes, tenants, plans, customerMaster, billingAuditLog)

Loader: `services/legacy-billing/migration/mongodb/load_units.py` (spec-driven: one mapping-spec collection per unit, `key`/`fields`/`embeds`/`indexes` straight from `mapping_spec.json`, loader obligations from `units.json` as per-unit hooks; refuses any unit not in `--write-targets` or any `--target-db` not in `allowed_targets.json`; a reload is `delete_many({})` + `insert_many`, nothing is dropped). Recon wrapper: `services/legacy-billing/migration/mongodb/recon_unit.sh <unit> <fixture|live>` (does the `cd` the harness insists on, F63). ```bash
