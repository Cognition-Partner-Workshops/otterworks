## 2. Collection design decisions (PROPOSED — each needs a yes at STOP B)

| # | Decision | Proposal | Why |
|---|---|---|---|
| D1 | Keys | Source PK carried into `_id` (single-column PKs); `codes` uses `_key = "TYPE:VAL"` plus `_id` ObjectId. No ObjectId-only collections. | Recon needs a declared comparison key; ids are deterministic md5-uuids already. |
| D2 | Field naming | Target field = lower-cased source column, 1:1, **explicit BSON `null`** for NULL/empty (tolerance v1). | Every one of the 155 `CUSTOMER_MASTER` columns is auditable by eye; no silent drops. |
| D3 | String dates (`DD-MON-YY` VARCHAR2 ×~20 cols) | Carry verbatim (graded) **and** add a derived BSON-date twin (`signup_date`, `invoice_date`, …; ungraded, unit-tested). Unparseable → row migrates, marked in quarantine class `dirty_signup_dt` (50 expected). | Behaviour-preserving for the existing report SQL; gives the app real dates; no data invented. |
| D4 | CSV lists (`RELATED_ACCT_IDS`, `CHILD_ACCT_IDS`, `PROMO_CODES_CSV`, `GL_ACCT_CSV`) | Verbatim (graded) + derived array; malformed → class `bad_csv_list` (31 expected). | Same as D3. |
| D5 | EAV | Fold into `customers.attributes[]` (`{eav_id, attr_name, attr_value, attr_type, created_dt}`), not a `{name: value}` map. | Keeps duplicates/typing quirks; recon-gradable with element key `eav_id`. |
| D6 | `INVOICE_LINE` embed | Embed in `invoices.lines[]` (avg 8, max 25 → bounded). Orphans (no header) → `quarantine.invoice_feed_orphan_lines`, never dropped. | Runbook target; 37 orphans expected and counted. |
| D7 | Postgres versions/snapshots | `versions[]` embedded (2–12/doc, bounded); `document_snapshots` separate collection referenced by `document_id` (large `state_b64`). Orphan snapshots → quarantine (6); version gaps reported, not repaired (10). | 16 MB doc limit safety; snapshots are archive reads. |
| D8 | DynamoDB `files` | 1:1; `ns` attribute → `source_ns`; migration `ns` = `mongo_205236`. Orphaned S3 markers reported (40). | Avoids overloading the migration namespace field. |
| D9 | Package-owned tables | Separate `billing_invoices` (from `INVOICES`) vs bulk `invoices` (from `INVOICE_HEADER`) — two estates, two collections. `RATING_RESULTS` embeds in `rating_periods.results[]`; `INVOICE_LINES` embeds in `billing_invoices.lines[]`. | Makes each PL/SQL upsert a single-document op. |
| D10 | Package dispositions | All 5 packages → **app-side Python** (`services/legacy-billing/app/ow_billing/`), with the set-oriented reads (`usage_events` sum, overdue list, RPT-114) as aggregation pipelines. Package globals become return values. `FOR UPDATE` → transaction. `WHEN OTHERS THEN NULL` → explicit `DuplicateKeyError` no-op only (other errors surface). NULL-propagation arithmetic (`LEAST/GREATEST/NVL`) reproduced exactly; grading is the 24 recorded transcripts (Tier 4). | Behaviour-preserving; the quirks are observable in transcripts. |
| D11 | Triggers/sequences/jobs | Sequences → `counters` collection (registered, U1 seeds at last_number); history triggers → app write path; `USAGE_EVENTS` check → `$jsonSchema`; audit purge → TTL index; nightly dunning → app scheduler shipped disabled. | No server-side triggers in Atlas M0. |
| D12 | Excluded | `FIXTURE_META` only. | Fixture bookkeeping; no reader. |
| D13 | Postgres / DynamoDB recon adapters | The harness ships `oracle`/`sqlserver`/`mongodb-atlas` source adapters only. U3/U4 use a thin adapter extension (`.migration/recon_ext/` — `PostgresSourceAdapter`, `DynamoSourceAdapter` implementing the harness `SourceAdapter` protocol); engine, tiers, tolerances and report are the harness's, unchanged. Logged as PROFILE FEEDBACK for the plugin. | Verdicts still come from the harness; nothing is hand-graded. |

Tier-4 replay for U6–U9 mutates data (`sp_*`), so each proc unit replays against its **own
registered clone** `replay_<unit>_*` of the wave-2 collections, never the golden loaded set.

**Width (recommendation, needs your pick):**
- **Option 1 — recommended: full fan-out via the dynamic workflow**, one child per unit; children
  boot their own deterministic `NS=demo` fixture (manifest checksum pinned; `make infra-up seed-legacy
  oracle-billing-up oracle-billing-seed NS=demo`) and self-verify in `fixture` mode; the parent's
  single LIVE window (cap 1) runs the independent wave recon on this VM. Widths: wave 0 = 1,
  wave 1 = 4, wave 2 = 3, wave 3 = 2. ~10 units / 230k rows sits at the single-session threshold,
  but the proc units are judgment-heavy and XL U1 benefits from isolation.
- **Option 2: width-1 inline** — all units sequential in this session (no fan-out; recorded as
  "width-1, running inline"). Slower wall-clock, no fixture re-boot ceremony.

Source-load behaviour: read-only; extracts use `${batch_no}`-scoped queries; one live connection
at a time (cap 1). Merge authority: recon `result.json` (LIVE, parent-run) per wave.
