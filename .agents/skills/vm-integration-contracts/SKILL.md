# VM integration contracts

Facts below are pinned to commit `e4e390e717b7e4dc83dc7600d525f9f482d253ef`. Re-read the linked lines if the code has moved on; the pinned source wins over any wiki or earlier answer.

Decision this rule records: https://partner-workshops.devinenterprise.com/sessions/62eb05cb436d4945bbea3a90b60789e2

## The rule

1. **Make the identity and data contracts explicit.** Before an application or its neighbour moves, write down what it trusts about the caller and every file it produces or consumes, citing the source lines.
2. **Prove compatibility before retiring a VM integration.** A working platform deployment, a demo run or an HTTP 200 from a stand-in is not that proof, and not permission to retire the integration (including dropping NFS).
3. **Preserve the producer's contract while a retained consumer stays.** If the producer moves first, it keeps the same file path semantics, file and date naming, schema and column order, atomic publication, and previous-day and missing-file behaviour that the consumer relies on.
4. **Engineering does not decide sign-in or acceptance.** Which sign-in route the desk accepts, and whether the result is acceptable, belong to the business owner. Engineering also does not decide HA, compliance or business-date timezone on its own; record them as open owner decisions.

## Current state for fx-report

- Sign-in is done by Apache, not the application: Basic auth via `mod_authnz_ldap` against `ldap://ldap.bank.internal`, restricted to `cn=fx-desk` ([fx-report.conf L2-L13](https://github.com/Cognition-Partner-Workshops/otterworks/blob/e4e390e717b7e4dc83dc7600d525f9f482d253ef/industries/banking/vmware-wave-1/fx-report/vm/fx-report.conf#L2-L13), [HOST.md L7](https://github.com/Cognition-Partner-Workshops/otterworks/blob/e4e390e717b7e4dc83dc7600d525f9f482d253ef/industries/banking/vmware-wave-1/fx-report/HOST.md#L7)).
